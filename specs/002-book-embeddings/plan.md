# Implementation Plan: Book Embedding Pipeline

**Branch**: `002-book-embeddings` | **Date**: 2025-12-12 | **Spec**: [specs/002-book-embeddings/spec.md](spec.md)

**Input**: Feature specification requires building a fully automated pipeline that crawls deployed Docusaurus book URLs, extracts clean text, generates embeddings via Cohere, stores vectors in Qdrant Cloud, and produces verification logs. Target outcome: reproducible embedding system for RAG chatbot usage.

## Summary

Build an automated, locally-runnable Python pipeline that:
1. Discovers all public URLs from a deployed Docusaurus book
2. Extracts clean, semantic text from each page
3. Chunks content into embeddings-ready segments with metadata
4. Generates 4096-dimensional embeddings using Cohere API
5. Stores vectors + metadata in Qdrant Cloud (Free Tier)
6. Produces JSON logs tracking ingestion stats and deduplication

**Key architectural decisions**:
- Single Python script/FastAPI job with UV package management for reproducibility
- Sitemap-based crawling (faster than recursive discovery) with fallback HTML parsing
- Stream processing to Qdrant to avoid memory overload on large books
- Content-based deduplication using SHA256 hashing pre-embedding
- Exponential backoff retry logic for transient API failures

## Technical Context

**Language/Version**: Python 3.11+
**Primary Dependencies**:
- `httpx` or `requests` (HTTP crawling with timeouts)
- `beautifulsoup4` (HTML parsing and text extraction)
- `cohere` (official SDK for embeddings)
- `qdrant-client` (Qdrant vector database client)
- `pydantic` (configuration and validation)
- `python-dotenv` (environment variable management)

**Storage**: Qdrant Cloud (Free Tier, vector database; no local persistence required for vectors)
**Testing**: `pytest` with fixtures for mock Cohere/Qdrant APIs
**Target Platform**: Local Linux/macOS/Windows with Python 3.11+, internet access
**Project Type**: Single CLI/batch script (Python package with `uv` for dependency management)
**Performance Goals**:
- Crawl + extract: ≤ 1 second per page (500 pages < 10 min crawl time)
- Embedding generation: ≤ 2 sec/chunk (batching to reduce API calls)
- Total pipeline: ≤ 1 hour for 500 pages with ~5000 chunks

**Constraints**:
- Cohere API Free Tier rate limits (handle gracefully with exponential backoff)
- Qdrant Cloud Free Tier storage (~500MB typical for large book)
- Network interruptions (persist progress; resume on re-run)
- No hardcoded secrets; all API keys via environment variables

**Scale/Scope**:
- Support books with 100–1000 pages and up to 50k chunks
- Batch Cohere requests (8-16 chunks per request) to reduce API calls and latency
- Stream Qdrant upserts to avoid loading all vectors into memory

## Technical Decisions & Rationale

### 1. URL Discovery Strategy
**Decision**: Sitemap-based discovery with HTML fallback

**Rationale**:
- Docusaurus generates `sitemap.xml` automatically → fastest, most reliable discovery
- Fallback to recursive HTML crawling if sitemap unavailable (handles custom configs)
- Avoids JavaScript execution overhead (Playwright/Selenium would be slower)

**Alternatives Considered**:
- Recursive crawler (HTML links): slower, risk of infinite loops, harder to deduplicate
- Manual URL list: not scalable, requires user input for every book
- Docusaurus API: not all instances expose GraphQL/REST; sitemap is universal

### 2. Text Extraction Method
**Decision**: BeautifulSoup4 with semantic tag targeting

**Rationale**:
- Docusaurus uses semantic HTML (article, section, p tags)
- BeautifulSoup4 is lightweight and widely available
- Targets `.docusaurus-page` or `<article>` to exclude nav/footer boilerplate

**Alternatives Considered**:
- Playwright/Selenium: overkill for static HTML; slower; higher memory
- Regex: fragile, harder to maintain across page layouts
- Trafilatura: overkill; BS4 sufficient for structured Docusaurus pages

### 3. Chunking Strategy
**Decision**: Semantic paragraph-based with max token count (512-1024 tokens/chunk)

**Rationale**:
- Cohere embed-3-large expects up to 512 tokens per text; stay conservative (512 max)
- Natural paragraph boundaries preserve semantic coherence
- Metadata (chunk_id, url, offset) enables retrieval of full context later

**Alternatives Considered**:
- Sliding window: overlapping chunks; complexity and duplication risk
- Fixed token count: loses semantic boundaries; harder to read in retrieval
- Sentence-based: too granular; leads to 10k+ chunks per book; API call overhead

### 4. Embedding Generation
**Decision**: Cohere `embed-3-large` with batch requests (max 8 texts per API call)

**Rationale**:
- Official Cohere SDK; well-documented
- Batch mode reduces API calls (1 call for 8 chunks vs. 8 calls)
- Exponential backoff (max 3 retries) handles rate limiting gracefully
- Free Tier supports ~1M tokens/month; typical book ≤ 5M tokens (fits within quota)

**Alternatives Considered**:
- OpenAI embeddings: cost per token; Cohere Free Tier more generous
- Local models (sentence-transformers): slower, no need for custom fine-tuning
- Async batch jobs: adds complexity; not needed for <1hr pipeline

### 5. Vector Storage & Deduplication
**Decision**: Qdrant Cloud with SHA256 content hash for deduplication

**Rationale**:
- Qdrant Cloud Free Tier: 25GB storage, HTTP API, no management overhead
- Content hash (SHA256) pre-embedding detects duplicates fast; skip re-embedding
- Upsert (not insert) prevents duplicate vectors if content hash already exists
- Metadata stored alongside vector (url, chunk_id, text) for retrieval context

**Alternatives Considered**:
- Vector similarity search to detect duplicates: expensive (querying after embed); hash is O(1)
- Milvus/Weaviate: more complex setup; Qdrant Cloud simpler for Free Tier
- Local SQLite for dedup log: reduces reliability; Qdrant is SSOT

### 6. Configuration Management
**Decision**: Environment variables + optional YAML config file

**Rationale**:
- Environment variables: secure (no hardcoded secrets in git), standard practice
- Optional YAML: allows advanced users to define custom book root, filtering rules
- Pydantic validation: catches config errors early before pipeline runs

**Alternatives Considered**:
- CLI arguments only: verbose for multiple runs; config file is more maintainable
- Hardcoded defaults: not flexible; requires code changes for different books

## Phase 1: Design & Contracts

### Data Model

**Key Entities**:
1. **Page**: Discovered URL, title, raw HTML content
2. **Chunk**: Extracted text segment with parent URL, chunk_id (hash), text content
3. **Vector**: 4096-D embedding from Cohere; includes chunk metadata and timestamp
4. **IngestionLog**: Summary statistics (URLs processed, chunks created, vectors stored, timestamps)

Full entity definitions in `data-model.md` (generated in Phase 1).

### API Contracts

**Cohere Client**:
- `POST /embed` → Cohere API for batch embedding
- Input: list of texts (max 8), model: "embed-3-large"
- Output: list of 4096-D vectors
- Error handling: rate limit (429) → exponential backoff; invalid request (400) → log and skip

**Qdrant Client**:
- `PUT /collections/{collection_name}` → Create collection if not exists
- `PUT /collections/{collection_name}/points` → Upsert vectors with metadata
- `GET /collections/{collection_name}` → Verify vector count

Full contracts in `contracts/` (generated in Phase 1).

## Risks & Mitigation

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Cohere API quota exceeded (Free Tier limit) | Pipeline stalls mid-way | Batch requests; estimate tokens beforehand; log consumption; optional --dry-run mode |
| Qdrant Cloud storage full | Cannot store vectors | Pre-calculate storage (≤ 500MB for typical book); support collection cleanup |
| Network timeouts during crawl/embedding | Partial ingestion; data loss | Checkpoint progress to local JSON; resume on re-run from last successful chunk |
| Malformed Docusaurus pages (unusual HTML) | Extraction failures | Graceful fallback to raw text; log failed pages; continue with other pages |
| Duplicate detection false positives | Skip legitimate unique chunks | Use content hash (SHA256); extremely low collision risk; document assumptions |
